## Medium-severity findings

### Item 9 — `_jax.devices()` raises at import without try/except
**Location:** `lifecycle/__init__.py:151` (`_check_runtime_platform`)
**Severity:** MEDIUM
**Description:** `devices = _jax.devices()` is called at import time. `_check_runtime_platform()` is invoked unconditionally on `import lifecycle`, with no try/except around it. Most failure modes here (no JAX, no device, plain CPU build) are handled internally by JAX. But on a misconfigured GPU instance — wrong CUDA toolkit version, partially loaded NVIDIA driver, broken cuDNN install — `_jax.devices()` can raise `RuntimeError` from the CUDA backend. That error propagates out of the import and prevents *any* `from lifecycle...` import in the rest of the run, including the runner script's pre-flight error handling.
**Failure mode:** import-time crash. Fails the entire `python verify_smoke.py` invocation with a stack trace before the script can print "GPU not configured correctly" or the `[lifecycle] WARNING: GPU env hints set ... but JAX reports CPU only` message that exists for exactly this case.
**Reproducibility:** any GPU instance where the JAX wheel is mismatched against the host CUDA runtime, or where `nvidia-smi` works but the runtime libs are missing. Triggered by any `import lifecycle` after a flaky AMI bootstrap.
**Recommended fix:** wrap the `_jax.devices()` call in `try/except RuntimeError` and print the existing warning ("WARNING: GPU env hints set but JAX reports CPU only") plus the exception text; do not re-raise. The whole purpose of the warning was to *catch* this category — the current code only catches the silent-CPU-fallback path, not the loud-CUDA-error path.
**Confidence:** MEDIUM. I have not exercised the failure path; the diagnosis is from reading the JAX backend init code in past sessions.

### Item 10 — `gpu_run.sh` crashes ungracefully if `aws` CLI is missing
**Location:** `scripts/gpu_run.sh:96, 120, 128`
**Severity:** MEDIUM
**Description:** The script invokes `aws s3 sync ...` and `aws s3 cp ...` directly. If the AWS CLI is not installed (e.g., a fresh AMI without the deep learning preinstall), the very first invocation at line 96 fails with `command not found`. Because of `set -euo pipefail`, the script exits before the `|| echo "[gpu_run] cache pull failed"` would trigger — `||` only catches non-zero exit, but a missing command raises a shell error that the script's strict mode does not redirect through `||`. Net effect: the script aborts with a single line of stderr, no Python is ever invoked, and the cache, log, and bundle phases all skip.
**Failure mode:** silent-ish abort before solver run. The user sees the wrapper print its banner, then nothing — easy to misread as "the solver crashed instantly".
**Reproducibility:** any AL2023 base AMI without the AWS CLI plugin pre-installed, any custom AMI built from `dnf install`-only scripts.
**Recommended fix:** at the top of the script, after `set -euo pipefail`, add a `command -v aws >/dev/null 2>&1 || { echo "[gpu_run] FATAL: aws CLI not found; install with 'dnf install -y aws-cli' or skip cache S3 sync"; exit 2; }`. Alternatively, gate each `aws` call behind a `command -v aws` check and silently skip with a warning. Choose based on whether S3 sync is required or optional for the run.
**Confidence:** HIGH (read of the script + shell semantics).

### Item 12 — `_compile_cache_sync.py` raises `FileNotFoundError` if `aws` CLI is missing
**Location:** `lifecycle/_compile_cache_sync.py:43, 67`
**Severity:** MEDIUM
**Description:** Both `pull_from_s3` and `push_to_s3` invoke `subprocess.run(["aws", "s3", "sync", ...], check=False)`. If `aws` is not on `PATH`, `subprocess.run` raises `FileNotFoundError` *before* the subprocess is launched — `check=False` only catches non-zero exit codes from the spawned process, not the spawn failure itself. The exception bubbles up through `pull_from_s3` and out to the caller, breaking any runner script that calls these helpers without its own try/except.
**Failure mode:** `FileNotFoundError: [Errno 2] No such file or directory: 'aws'` from inside Python, hard to map back to "AWS CLI is missing" without reading the traceback carefully.
**Reproducibility:** any host where the runner script imports `_compile_cache_sync` but the AWS CLI is not on `PATH`. More likely on dev laptops where someone tries the helper interactively than on production AWS.
**Recommended fix:** wrap each `subprocess.run` in `try / except FileNotFoundError` and return `127` (the conventional shell exit code for command-not-found) plus a `print` explaining the cause. Document in the module docstring that `aws` CLI is required.
**Confidence:** HIGH (CPython subprocess semantics).

- **Item 17 — Concurrent `gpu_run.sh` invocations clobber the cache directory.** [gpu_run.sh:94-102, 119-121]. Two simultaneous `gpu_run.sh` runs against the same instance share `LIFECYCLE_JAX_CACHE_DIR`. The "non-empty → skip pull" check is racy (process A pulls, process B sees half a directory and skips), and the trailing `aws s3 sync` push is per-file atomic but not per-directory atomic. Foreseeable scenario: a developer ssh'es into the instance and starts a second run while the userdata-driven first run is still warming the JIT — both push partial caches with size-based dedup, and a poisoned partial entry can survive into the next run. Fix: hold a flock on the cache dir for the duration of the run, or write to a per-run temp dir and `aws s3 sync --delete` only on success.

## Items reported as NO

- **Item 1 — `_newton_fori` mask correctness.** [solver.py:559-650]. `is_active = NOT(converged OR ls_failed)` masks all field updates once a cell terminates. `n_used` increments only on active iters (`n_used + jnp.where(is_active, 1, 0)`) — diagnostic-correct. Final exit code `jnp.where(converged, EC_INTERIOR, EC_NEWTON_FAIL)` correctly distinguishes the three terminal states (converged, line-search-failed, ran-out-of-iters); ls-failed-then-converged cannot happen because both flags freeze on first set.

- **Item 2 — `_backtracking_fori` first-success semantics.** [solver.py:501-556]. The `improved_now = NOT(found) AND err_t < err_old` gate is the correctness-critical line; `found` is monotone (once True, stays True), so subsequent halvings cannot overwrite the first-success state. The `alpha` field uses `jnp.where(found, alpha, new_alpha)` — held at first-success value once `found=True`. The init seeds `found = full_improves`, matching the `while_loop` version's "if alpha=1 improved, exit immediately" exit. Both versions produce identical post-iteration state for any finite halving sequence.

- **Item 3 — Warm-start under checkpoint resume.** [solver.py:1973-2014, 2078-2122]. The `if solved_age_mask[t]: continue` guard at line 2084 fires *before* `c_next_jnp = C_list[t+1]` (line 2089), so unsolved-age branches never read solved-age policy slots. For any age `t` we solve, `t+1` is older — solved either by the resume loop (line 2003-2006) or by an earlier loop iteration. The resume's broadcast-lost concern is moot: terminal age's `jnp.broadcast_to(...)` is materialised by `np.asarray()` in `_materialize_policy_lists` before save; on reload, indexing `init_a_s_arr[z_idx, i_s, w_ref_idx]` on the materialised array returns the same scalar regardless. Memory cost of ~`(n_z-1)/n_z` extra at terminal is paid once, harmless at canonical sizes.

- **Item 4 — `n_dev` dispatch correctness.** [solver.py:1436-1440, 1549-1553, 1681-1685]. Verified all six call signatures pairwise: terminal `call(_unused_age_idx=None)` matches; retirement `call(c_next, pension, psi, init_a_s, init_a_b)` matches; working/boundary `call(c_next, income_table, pension, psi, init_a_s, init_a_b)` matches. `len(jax.devices())` is documented to return ≥1 even on a host with no real accelerators; no `n_dev=0` reachable. The else branch goes to `_pmap` for any `n_dev > 1` including the multi-GPU "pmap is suboptimal but correct" case the handoff calls out as known.

- **Item 6 — NaN/Inf propagation paths.** All identified divisions are guarded:
  - Newton det: `1.0 / jnp.where(is_singular, 1.0, det)` (line 421, 599) — singular path handled.
  - Wealth interp: `1.0 / (x1 - x0)` (line 807, 873) — `wealth_grid = expm1(linspace(...))` is strictly increasing by construction in `precompute._build_grids`.
  - `c_at_xn ** (-gamma)` (line 998) — preceded by `c = jnp.maximum(c, min_consumption)` inside `_interp_c_and_mpc_at_cell` (line 832) and `per_kv_kr` (line 883), so c ≥ 1e-10 (default).
  - `beta_e ** (-1.0/gamma)` (line 1082) — preceded by `beta_e = jnp.maximum(beta * V_dot, euler_inv_floor)`, so beta_e ≥ 1e-20 (default). At gamma=10, gives `1e-20**(-0.1) = 1e2` — finite.
  - `bequest_mu_and_mup`: `C_bar = W/A + delta` with A>0 (annuity factor), delta>0 (default 1e-3). C_bar always positive, mu/mup finite.
  - `jnp.sqrt(fs² + fb²)` — sum of squares is non-negative; safe.

- **Item 7 — Integer overflow / dtype.** [solver.py:1584, 1646, 1715, 1805, 783]. `np.arange(..., dtype=np.int64)` for cell index arrays. `astype(jnp.int32)` for `j` corner indices is safe at canonical 4-D (max axis size 15 → max flat index ~50,000, well below 2^31). `jnp.searchsorted` returns int32 by default, used only to index n_w-sized arrays — fine. The shape `(n_age, n_z, N_state, n_w)` total element count at canonical 4-D `(80, 11, 14641, 180)` is 2.32e9 — exceeds int32 limit, but NumPy uses `Py_ssize_t` (int64-equivalent on 64-bit hosts) for shape arithmetic. No overflow.

## Other observations (off-checklist)

- **`policy_io.py:149` — `spec = "simple_clamp"` default.** The only `wealth_dynamics_spec` the JAX solver accepts is `"ccv_log"`. The `save_policy_bundle` default of `simple_clamp` writes a stale tag into bundle metadata when `run_config` is None or lacks `solver_config`. Not a runtime bug — it's a tagging issue, but it could mislead the diagnostic-loader's "verify the simulator runs under the same spec the solver used" check. Suggest changing the default to `"ccv_log"` or to `None` (and have downstream consumers tolerate `None`).

- **`solver.py:1230-1231` — c_corners memory at canonical 4-D state.** At `n_state=4`, `c_corners_T` shape is `(n_state_quad, n_z, 2^4, n_w) = (n_state_quad, 11, 16, 180)`. Per cell that's about 6 MB; under vmap over `n_cells = 161,051`, the materialised batch is ~1 TB if XLA materialises in full. XLA usually streams gathers, but this is the single biggest GPU memory risk for the 4-D state extension. The existing comment at line 1227 mentions this concern for `n_state=3` ("~3MB/cell, verified small enough at canonical sizes"); the `n_state=4` numbers should be re-verified before the first 4-D run on GPU. **This is a forward-looking risk only — flagged but not actionable as a "bug".**

- **`solver.py:240, 251, 271` — `searchsorted` on a sorted grid.** All three calls assume the search target grids (wealth_grid, axis_grid) are strictly monotone. `precompute._build_grids` produces them via `expm1(linspace(...))` and the discretization machinery, both monotone in normal use. If a future refactor introduces a degenerate grid (e.g., zero-width bracket), `searchsorted` returns a clamped index but the downstream `inv_dw = 1 / (x1 - x0)` would NaN. Would defeat the existing FOC guards. Defensive concern only — no bug today.
